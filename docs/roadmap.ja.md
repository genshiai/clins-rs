# clins-rsの使いどころと開発予定

基準日：2026-11-19。以下は開発計画の目安であり、自動実行の予約や国の受入日程ではありません。
現時点のコード・配布物は [v0.1.0-alpha.2](https://github.com/genshiai/clins-rs/releases/tag/v0.1.0-alpha.2) です。

## 完成させるものを分ける

| 対象 | 担当すること | 完了の確認方法 |
|---|---|---|
| clins-rs | 生成済みFHIR JSONを固定版の規格定義で検証する | 対応規則・正常／異常試験・未対応条件を追跡でき、各SDKで同じ判定になる |
| 電子カルテなどの利用アプリ | 元の記録をFHIRへ変換し、不足情報の入力、検証結果の表示、発行・保存を行う | 架空データで入力から生成・検証・保存までの操作試験が通る |
| 共有サービスへの送受信機能 | 接続・認証・送信・応答・再送・重複防止・結果管理を行う | 医療機関の接続検証環境で、指定された運用テストを完了する |
| 配布 | CLIやSDKを入手・導入できるようにする | GitHub成果物と、登録した各レジストリから導入できる |

生成器と検証器は別の部品です。たとえば病名の標準コードが不足したJSONについて、
clins-rsは問題を検出します。適切なコードを選び直す画面や、元の記録との対応付けはアプリ側に必要です。
`valid` だけで臨床上の承認や共有サービス側の受入が成立するわけではありません。

CLINS公式のValidationガイドも、作成済みJSONがプロファイルに準拠しているかの検証を説明しています。
現在の公式手順で使うJava Validatorとの比較は開発時の確認手段です。
clins-rsの利用時にJavaプロセスを起動する構成にはしません。
出典：[CLINS Validationガイド](https://jpfhir.jp/fhir/clins/igv1/validationGuide.html)。

## 予定と完了条件

単独の主担当が継続して開発し、大きな仕様変更がない前提です。
日付は着手・確認の目安です。規則の棚卸しで大きな不足が見つかった場合は、完了条件を維持して日程を見直します。

| 時期の目安 | 作業 | 完了条件 |
|---|---|---|
| 11/19 | 日本語READMEと実際の利用手順を整える | CLI・HTTP・SDKの使い方と、生成／検証／送信の担当が明確になる |
| 11/20〜11/27（3〜5営業日の作業目安） | 利用アプリとの接続を確認する | エンジン識別子・固定パッケージ・レポート判定条件を点検し、JSON生成→新Validator→画面表示→保存を正常・異常・未完了で確認する。必要な認証・DB等は利用アプリ側の環境で用意する |
| 11/20〜12/4（並行して約2週間） | 対象版の規則と試験の対応表を作る | プロファイル、継承規則、用語、参照、本文記載の条件を棚卸しする。各規則に適用条件・試験ID・未対応理由を付け、残作業を再見積もりする |
| 12/7以降（棚卸し後、追加で2〜6週間を仮置き） | 未対応条件を補完しβ候補を作る | 対象範囲で判定不能になる条件を補完する。境界値・異常系・参照Validatorとの差分を確認し、各SDKで試験する。一般的な日付・Quantity境界や外部用語の未解決条件も、対象内／対象外を明記する |
| アカウント・名前空間の準備後（作業1〜3営業日程度、審査待ちを除く） | crates.io・PyPI・npm・Maven Centralへ登録する | 所有者・パッケージ名・公開用認証を確認し、各配布物を実際に導入して同じ架空例を検証できる。開発・接続試験とは並行可能 |
| 医療機関の接続検証環境が利用可能になった後 | 利用アプリの国サービス接続試験を行う | 現行の技術解説書と指定テスト項目に沿い、送信・応答・エラー・再送等を確認する。試験枠・申請・相手側の対応期間が未確定なので、現時点で完了日を約束しない |

ライブラリのβ候補は、現時点では **約1〜2か月を仮の開発目安** とします。
すべてのFHIR仕様・臨床要件の完全適合や国の接続完了までを、その期間で保証する見積もりではありません。
最初の約2週間で規則別の不足を明確にし、β候補の日程と対象範囲を更新します。

## 「全規則の適合確認」をどう進めるか

現在の131定義・4,472件は、JP Core／CLINSの差分に明示された規則の一覧です。
85件のRust試験や、SDK共通28ケースが、4,472件すべてを個別に確認したことにはなりません。
継承されるR4の規則や、本文中の条件も別に確認する必要があります。

次の成果物は「完全適合」という表示を付けることではなく、規則ごとの検証根拠です。

1. 固定するFHIR・JP Core・CLINS・用語パッケージの版とSHA-256を明示する。
2. 規則にIDを付け、適用条件・実装箇所・試験ID・未対応理由を対応付ける。
3. 適用される規則ごとに正常・異常・必要な境界値を確認する。異常例が成立しない規則は理由を残す。
4. 独立した期待結果と参照Validatorの結果を照合し、差異を説明する。
5. 未対応の判定を成功扱いしないこと、各SDKで結果が一致することを確認する。

規格の機械的な適合確認、臨床内容の正しさ、国の運用テストは、それぞれ異なる確認です。
この一覧だけで国の認定や公式のお墨付きを主張しません。

## 国の接続試験に必要なもの

利用医療機関、現在の申請手順、接続検証環境、指定テストデータ、接続方式と認証設定、
利用アプリの送受信機能をそろえます。認証情報や実患者データをGitHubやチャットへ置く必要はありません。

2026-11-19に確認した公式ポータルでは、オンライン資格確認の利用が前提であり、
利用申請は接続検証環境での運用テストに必要な手続きと説明されています。
申請登録は約1週間との案内ですが、これは開発・試験全体の所要期間ではありません。
出典：[電子カルテ情報共有サービスの利用申請](https://iryohokenjyoho.service-now.com/csm?id=kb_article_view&sysparm_article=KB0010245)。

また、公式ポータルの2026/10/07付案内には、令和8年度冬頃の技術解説書（運用開始版）公開予定が記載されています。
接続試験へ進む際には、その時点の公開版と対象サービスの条件を再確認します。
出典：[電子カルテ情報共有サービスの導入に係る補助金・関連案内](https://iryohokenjyoho.service-now.com/csm/ja?id=kb_article_view&sys_kb_id=5e95cdd12bfb0f107852f7ac6e91bf4b)。

## 登録配布に必要なもの

公開先ごとの所有アカウント・組織、利用可能なパッケージ名／名前空間、公開権限を確定します。
認証は各サービスの正式な方法で設定し、設定後に導入確認を行います。
GitHub Releaseの成果物はすでに利用でき、レジストリ登録を待つ必要はありません。

Maven Centralの名前空間は、現在の `jp.genshi` で所有確認できるかも含めて確認します。
認証設定や名前空間の準備がない状態では、登録作業の完了日を確定しません。

現在の実装上の制限は [対応範囲](coverage.md)、技術的な残件は [remaining-work.md](remaining-work.md) を参照してください。
